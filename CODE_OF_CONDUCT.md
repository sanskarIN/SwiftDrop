# SwiftDrop Code of Conduct

SwiftDrop is an open-source project. Everyone participating in the repository, issue tracker, pull requests, reviews, support channels, and other project-managed community spaces is expected to help keep collaboration safe, respectful, technically constructive, and privacy-conscious.

## Expected behavior

Participants should:

- communicate respectfully and professionally;
- critique ideas, code, tests, and documentation rather than attacking people;
- assume good faith while still asking for evidence when technical claims matter;
- accept correction when a claim, implementation, or review is wrong;
- give actionable feedback rather than insults or dismissive comments;
- respect different experience levels, languages, backgrounds, identities, and accessibility needs;
- keep discussions relevant to the project or clearly identified support topic;
- protect user privacy and avoid sharing unnecessary personal/sensitive information;
- disclose conflicts of interest when they materially affect a technical or moderation decision;
- cooperate with maintainers when a conversation must be moved, redacted, or made private for security/privacy reasons.

## Unacceptable behavior

The following are not acceptable in project-managed spaces:

- harassment, intimidation, threats, stalking, or sustained personal attacks;
- discriminatory or demeaning language based on identity or personal characteristics;
- sexual harassment or unwanted sexualized comments/content;
- doxxing or publication of private personal information without permission;
- publication of private transfer contents, credentials, keys, pairing capabilities/nonces, or other user secrets;
- deliberately encouraging users to bypass security controls in order to “make SwiftDrop work”;
- spam, scams, impersonation, malicious links, or deceptive support messages;
- knowingly false claims about security, privacy, test results, release readiness, or project ownership;
- repeated disruption of technical discussions after moderator direction;
- retaliation against someone who raises a good-faith security, privacy, accessibility, or conduct concern.

## Security and privacy discussions

Security findings can require private handling. If a report contains exploit details, private keys, pairing capabilities, real user files, sensitive logs, or other security-sensitive information, follow `SECURITY.md` rather than posting the details publicly.

Maintainers may redact or remove sensitive information from public discussions even when the original poster acted in good faith.

## Technical disagreements

Strong technical disagreement is allowed. Keep it evidence-based.

Good disagreement includes:

- citing source behavior or tests;
- presenting a minimal reproduction;
- explaining threat/compatibility tradeoffs;
- proposing alternatives;
- acknowledging uncertainty;
- changing your position when new evidence is stronger.

Bad disagreement includes insults, status attacks, deliberate misrepresentation, or repeated demands that security/quality gates be bypassed without a technical basis.

## Maintainer responsibilities

Project maintainers may:

- edit/remove abusive, discriminatory, spammy, or privacy-violating content;
- ask participants to stop or redirect disruptive behavior;
- lock or close discussions that are no longer productive;
- remove sensitive material from public view;
- temporarily or permanently restrict participation in project-managed spaces when necessary.

Moderation should be proportionate to the behavior and should prioritize safety, privacy, project integrity, and a workable collaboration environment.

## Reporting conduct problems

For a non-security conduct concern involving a public thread, use the repository's appropriate reporting/moderation features or contact the project privately when public discussion would worsen the problem.

For security vulnerabilities or sensitive technical disclosures, follow `SECURITY.md`.

## Scope

This Code of Conduct applies to project-managed spaces and to conduct performed in an official project representative capacity.

It does not give maintainers control over unrelated private activity, but external conduct may be considered when it directly threatens project participants, user privacy, repository security, or credible project representation.

## Good-faith enforcement

Enforcement decisions should not be used to suppress legitimate criticism, responsible vulnerability reporting, evidence-based technical disagreement, or respectful questions about project decisions.

The goal is a project where contributors and users can report problems, disagree, learn, and improve the software without harassment, deception, or avoidable privacy/security harm.
