# SwiftDrop 2.5.18 — Draft Release Notes

Status: **draft candidate notes — not yet a published production release**

SwiftDrop 2.5.18 is being prepared as the next coordinated release milestone. These notes describe the integrated source-level candidate scope and must be finalized against the exact merged candidate before publication.

## Highlights

### Maintained Linux desktop support

SwiftDrop adds a dedicated Avalonia desktop host for Linux while continuing to share the security-sensitive `SwiftDrop.Core` implementation with the existing application surfaces.

The maintained Linux path includes:

- `linux-x64` and `linux-arm64` self-contained packaging;
- XDG-aware local data/identity paths;
- nearby/manual/link pairing;
- mDNS and UDP discovery;
- file, folder/batch, resumable, and text sending;
- explicit receive approval, storage preflight, collision protection, and SHA-256 verification;
- native desktop file/folder pickers and clipboard integration;
- dependency/vulnerability audit evidence in hosted CI.

Linux is intentionally implemented as a dedicated desktop host because .NET MAUI does not provide an official Linux desktop target.

### Cross-platform release-version consistency

The 2.5.18 candidate aligns maintained release identifiers across:

- Android/iOS/Mac Catalyst/Windows MAUI app: `2.5.18`;
- MAUI application build/version code: `20518`;
- iOS Share Extension: `2.5.18` / `20518`;
- Windows package identity: `2.5.18.0`;
- Avalonia desktop host: `2.5.18`.

An automated version-alignment validator fails CI if these package surfaces drift.

### Stronger release-readiness gates

The candidate release pipeline now treats Linux as a first-class maintained release-gate platform rather than a side workflow only.

Release readiness includes:

- portable Core/tests and validation helpers;
- Android hosted compile/dependency audit;
- focused Windows hosted compile/dependency audit;
- Mac Catalyst hosted compile/dependency audit;
- iOS containing app + Share Extension hosted compile/dependency audit;
- Linux `linux-x64` and `linux-arm64` package build/dependency audit;
- CodeQL and repository security hygiene;
- aggregate failure if any maintained source/platform gate fails.

Linux integration and cross-platform version alignment also run from common CI and portable Bash/PowerShell verification paths. Manual release-evidence validation/generation/status tooling remains part of the release-critical workflow surface.

### Final hardening and interface polish

The 2.5.18 candidate contains the final post-v1 hardening/UI work preserved from the August 19 integration, including expanded Core regressions, fail-closed release-evidence handling, localized navigation/settings/diagnostics/queue presentation, and accessibility/localization polish.

The hardened integration reached `main` through PR #34 as `c74eead16691ebd133d78c5fa8f279ba4c11acae`. Its history is preserved in the 2.5.18 candidate rather than reimplemented or squashed away.

### Repository governance hardening

The candidate now includes repository ownership/review policy hardening through:

- `.github/CODEOWNERS` with repository fallback ownership;
- explicit ownership for security, discovery, protocol, networking, transfer, storage, native MAUI platform code, Avalonia desktop, iOS Share Extension, Linux packaging, and sensitive documentation;
- machine-enforced CODEOWNERS validation in the repository-completion contract;
- regression tests that reject missing/reassigned sensitive ownership;
- a documented single-maintainer protected-change policy that avoids impossible self-review requirements.

The governance history from PR #36 is preserved through two-parent integration merge `cfeb728682c11c0f20eaaf9c63de775ae3d26716`.

Source-side governance does not imply that remote GitHub branch protection is enabled. The most recently inspected remote state reported `main` as not protected, so that remains separate repository-administration evidence.

## Platform scope

2.5.18 is prepared for the maintained source platforms:

- Android;
- iOS containing app;
- iOS Share Extension;
- Mac Catalyst;
- Windows;
- Linux desktop (`linux-x64`, `linux-arm64`).

## Security and privacy principles retained

The release continues to use the existing local-first SwiftDrop security model:

- account-free local transfer;
- peer certificate identity and fingerprint pinning;
- one-time authorization;
- bounded/strict protocol parsing;
- canonical cross-platform paths;
- SHA-256 integrity verification;
- collision-safe receive handling;
- privacy-minimal local metadata;
- no SwiftDrop-operated cloud relay required for transfer payloads.

## Not part of 2.5.18

The planned browser extension is deliberately deferred to the next feature milestone. Adding another large execution surface during 2.5.18 release stabilization would weaken the candidate-freeze boundary and enlarge the signing/testing matrix late in the cycle.

## Validation still required before publication

These draft notes do **not** mean the release is production-ready. Before publishing `v2.5.18`, the exact merged candidate still requires successful exact-head automated gates and the applicable signed/manual evidence for:

- Android signed AAB/APK install and upgrade behavior;
- real Android share providers, foreground/lifecycle, notification and local-network behavior;
- Windows signed MSIX install/update/protocol/app-notification/firewall behavior;
- Apple Developer provisioning/App Group configuration;
- signed iOS containing app + Share Extension provider/handoff behavior;
- signed/notarized Mac Catalyst behavior;
- representative Linux distribution/package execution;
- physical cross-platform pairing and file/folder/text/resume scenarios;
- network switching, restricted LANs, low storage and filesystem edge cases;
- TalkBack, VoiceOver, Narrator, keyboard, large-text/high-contrast and Hindi runtime validation;
- final signed-artifact dependency/license/notice/provenance reconciliation;
- final store metadata, screenshots, privacy declarations, signing/notarization, submission and review;
- remote GitHub branch/ruleset protection if it is part of the release governance requirement.
