# SwiftDrop 2.5.18 Release Preparation

Updated: 2026-08-24

Status: **source preparation in progress; not yet a signed production release**.

This document defines the repository-side release-preparation contract for SwiftDrop 2.5.18. It does not replace the release checklist, manual evidence manifest, signing guidance, or store/privacy review. A green source workflow is necessary but is not equivalent to signed-device or distribution validation.

## Release identifiers

The maintained package surfaces are aligned as follows:

| Surface | Release value |
| --- | --- |
| MAUI application display version | `2.5.18` |
| MAUI application build/version code | `20518` |
| iOS Share Extension display version | `2.5.18` |
| iOS Share Extension build version | `20518` |
| Windows package identity | `2.5.18.0` |
| Avalonia desktop host | `2.5.18` |

The integer build convention is `major * 10000 + minor * 100 + patch`, with minor and patch components limited to two decimal digits. For 2.5.18 this yields `20518`.

`scripts/validate_version_alignment.py` is the authoritative repository-side alignment check. It verifies the MAUI application, iOS Share Extension, Windows package manifest, and Avalonia desktop project together. The validator runs in common CI and both portable verification entry points.

## Intended 2.5.18 source scope

The release-preparation queue intentionally consolidates the post-closure work that was opened after the August 19 source-completion baseline:

- final Core/security/release-evidence hardening and UI/localization/accessibility integration from PR #34;
- maintained Linux desktop support from PR #35;
- repository ownership/review governance hardening from PR #36;
- the coordinated 2.5.18 package-version update;
- cross-platform version-alignment validation;
- Linux integration validation promoted into common portable CI;
- Linux x64 and arm64 build/package/dependency-audit coverage promoted into aggregate release readiness.

The browser-extension work is deliberately **not** part of 2.5.18. It remains a subsequent feature milestone so the 2.5.18 candidate can be frozen, validated, signed, and distributed without introducing another large platform surface during release stabilization.

## Automated source gates required before candidate freeze

Before selecting an exact 2.5.18 candidate commit, require successful exact-head results for:

- Python helper tests;
- repository completion validation;
- documentation validation;
- localization validation;
- Apple integration validation;
- Windows integration validation;
- Linux desktop integration validation;
- cross-platform version alignment validation;
- SwiftDrop.Core restore/build/tests;
- benchmark compilation;
- NuGet vulnerability validation;
- CodeQL;
- security hygiene;
- Android hosted compilation/dependency audit;
- Windows hosted compilation/dependency audit;
- Mac Catalyst hosted compilation/dependency audit;
- iOS containing app + Share Extension hosted compilation/dependency audit;
- Linux `linux-x64` self-contained package/dependency audit;
- Linux `linux-arm64` self-contained package/dependency audit;
- aggregate release-readiness gate.

Do not use a successful workflow result from an older commit as evidence for the final candidate.

## Exact-candidate rule

The release candidate is one immutable 40-character commit SHA on `main` after the intended integration queue has been merged and all repository-side preparation changes are complete.

Only after that SHA is selected should a fresh manual release-evidence record be generated:

```bash
python3 scripts/create_manual_release_evidence.py \
  --commit <40-hex-candidate-commit> \
  --version 2.5.18 \
  --output release-evidence/2.5.18.json
```

The generated record must begin with external cases in truthful `not-run` state. Do not copy pass states from a previous candidate.

## Signed and physical validation still required

### Android

- produce the intended signed AAB/APK from the exact candidate;
- verify install and upgrade behavior;
- exercise real `ACTION_SEND` and `ACTION_SEND_MULTIPLE` providers;
- test local-network discovery, permissions, notifications, lifecycle/background behavior, large files, low storage, pause/cancel/resume, and network changes on physical devices.

### iOS

- provision the containing app, Share Extension, and App Group using the intended Apple Developer configuration;
- verify the signed containing app embeds and communicates with the signed Share Extension correctly;
- exercise real `NSItemProvider` inputs, App Group handoff, expiry/malformed package handling, and review-before-send behavior;
- validate VoiceOver, large text, lifecycle, local-network permissions, and transfer flows on physical devices.

### Mac Catalyst

- build/sign the intended distribution artifact;
- validate sandbox/security-scoped access, native drop, pairing, transfers, notifications, lifecycle behavior, and notarization/distribution requirements.

### Windows

- build/sign the intended MSIX/distribution artifact;
- verify install/update, protocol activation, app-notification activation, firewall/private-network behavior, drag/drop and picker flows, and filesystem collision/resume behavior on representative systems.

### Linux

- exercise the generated `linux-x64` and `linux-arm64` packages on representative distributions/environments;
- verify executable permissions, desktop entry registration, `swiftdrop://` protocol handling, discovery/network behavior, file/folder pickers, clipboard integration, transfers, resume, storage limits, and filesystem permissions;
- reconcile packaged runtime/dependency contents with retained dependency evidence.

### Cross-device matrix

Exercise representative Android/iOS/macOS/Windows/Linux sender and receiver combinations for pairing, single files, folders/batches, text, resume, failure recovery, trust/revoke, collisions, restricted networks, and large payloads.

## Accessibility, localization, privacy, and store evidence

Before release approval:

- validate English and Hindi runtime presentation on real targets;
- test TalkBack, VoiceOver, Narrator and applicable desktop accessibility behavior;
- test large text, keyboard navigation, high contrast/system themes and non-color-only status communication;
- reconcile final signed binaries with `PRIVACY.md`, store privacy declarations, permissions, entitlements, dependencies, licenses, notices, and provenance evidence;
- produce current store screenshots/metadata from the approved candidate;
- complete signing, notarization where applicable, submission, review, and post-publication install/update verification.

## Tagging rule

Do not create or advertise `v2.5.18` as a production release until the exact candidate has passed the required automated gates and the applicable manual evidence record passes complete mode.

After all required evidence is complete:

1. verify the exact candidate SHA and version-alignment validator output;
2. validate the manual evidence record with `--require-complete`;
3. create the `v2.5.18` tag from that exact SHA;
4. publish release notes tied to that SHA and retained evidence;
5. distribute only artifacts built from that approved candidate.

## Current preparation boundary

Repository-side version preparation can be completed in Git. Signing credentials, production certificates/provisioning profiles, physical-device/network/provider testing, notarization, store submissions, and store review are external evidence and must not be represented as completed merely by changing repository files.
